# Figma MCP 구현 규칙

## 기본 작업 원칙

- 작업을 시작하기 전에 현재 프로젝트 구조와 관련 파일을 먼저 분석한다.
- package.json과 기존 소스코드를 확인하여 프레임워크, 스타일링 방식, 상태관리, 라우팅 방식을 파악한다.
- 기존 컴포넌트, 유틸리티, 디자인 토큰을 우선 재사용한다.
- 같은 역할의 컴포넌트를 중복 생성하지 않는다.
- 사용자의 명시적인 요청 없이 새로운 라이브러리를 설치하지 않는다.
- UI 작업을 위해 API, 라우팅, 데이터 구조, 비즈니스 로직을 임의로 변경하지 않는다.
- 관련 없는 파일은 수정하지 않는다.
- 기존 프로젝트의 네이밍, 폴더 구조, 코드 스타일을 유지한다.

---

## 1. 디자인 조회

1. 제공된 URL에서 Figma file key와 node-id를 파싱한다.
2. node-id를 모르거나 불확실하면 `get_metadata`로 전체 트리를 먼저 파악한 뒤 대상 node를 확정한다.
3. 대상 node를 확정한 후 `get_design_context`를 호출한다.
4. 응답이 너무 크거나 잘리면 필요한 하위 node만 나누어 `get_design_context`로 재조회한다.
5. 반드시 `get_screenshot`을 호출하여 시각적 기준 이미지를 확인한다.
6. 디자인 컨텍스트와 screenshot을 모두 확인하기 전에는 코드를 작성하지 않는다.

---

## 2. 구현 전 분석

코드 수정 전에 다음을 확인한다.

- 현재 프로젝트에서 사용하는 UI 프레임워크
- CSS, CSS Modules, Tailwind, styled-components 등 스타일링 방식
- 기존 공통 컴포넌트
- 색상, 폰트, 간격 디자인 토큰
- 이미지와 아이콘 관리 방식
- 라우팅과 상태관리 방식
- 재사용 가능한 기존 코드
- 생성하거나 수정할 파일 목록

구현 범위가 크면 작업 계획과 수정 예정 파일을 먼저 제시한다.

### 컴포넌트 재사용 판단 기준

기존 컴포넌트와 Figma 디자인을 비교하여 재사용 여부를 판단한다.

- **80% 이상 일치**: 기존 컴포넌트에 props 또는 CSS만 조정하여 재사용한다.
- **50~79% 일치**: 기존 컴포넌트를 수정하되, 다른 사용처에 영향이 없는지 확인 후 수정한다. 영향이 있으면 파생 컴포넌트를 생성한다.
- **50% 미만 일치**: 새 컴포넌트를 생성한다. 기존 컴포넌트를 무리하게 수정하지 않는다.

판단이 애매하면 사용자에게 확인한다.

## 3. 디자인 구현 기준

- Figma 디자인과 1:1 시각적 일치를 우선한다.
- Figma의 Frame 크기, 정렬, 간격, padding, gap을 정확히 반영한다.
- Auto Layout 구조는 적절한 flex 또는 grid 구조로 변환한다.
- absolute positioning은 Figma 구조상 필요한 경우에만 사용한다.
- 기존 디자인 토큰이 있으면 임의의 색상이나 간격 값보다 토큰을 우선 사용한다.
- 적절한 토큰이 없다면 Figma에서 확인한 정확한 값을 사용한다.
- Figma의 텍스트 내용을 임의로 수정하거나 요약하지 않는다.
- 폰트 family, weight, size, line-height, letter-spacing을 확인한다.
- border, radius, opacity, blur, shadow 값을 확인한다.
- hidden, overflow, fixed, sticky 등의 동작을 디자인 구조에 맞게 처리한다.
- 데스크톱과 모바일 디자인이 모두 있다면 각각의 Frame을 조회한다.
- Figma에 모바일 Frame이 없으면 기존 프로젝트의 breakpoint 규칙을 유지하고 임의로 반응형을 추가하지 않는다. 반응형 처리가 필요하다고 판단되면 사용자에게 확인한다.
- Hover, Active, Disabled, Loading, Empty 상태가 제공되면 함께 구현한다.

---

## 4. 이미지와 아이콘

- Figma MCP가 제공하는 실제 이미지와 SVG asset을 사용한다.
- asset이 제공됐는데 placeholder를 만들지 않는다.
- 제공된 아이콘을 임의의 이모지나 유사 아이콘으로 대체하지 않는다.
- Figma asset이 있는데 새로운 아이콘 패키지를 설치하지 않는다.
- 기존 프로젝트에 동일한 아이콘이 있으면 기존 asset을 재사용할 수 있다.
- 이미지 비율, object-fit, crop, border radius를 Figma와 동일하게 맞춘다.
- 사용할 수 없는 asset이 있으면 임의 대체하지 말고 사용자에게 보고한다.

---

## 5. 기존 코드 보호

- UI 구현 때문에 API 요청 형식을 변경하지 않는다.
- mock data를 실제 API 코드에 남기지 않는다.
- 기존 기능과 이벤트 처리를 제거하지 않는다.
- 디자인에 표시된 데이터는 현재 프로젝트 데이터 구조에 연결한다.
- 데이터가 아직 없으면 UI와 데이터 연결 지점을 명확히 분리한다.
- 기존 페이지 전체를 재작성하기보다 필요한 범위만 수정한다.

---

## 6. 검증

구현 후 다음 검증을 반드시 수행한다.

1. 프로젝트를 로컬에서 실행한다.
2. Figma Frame과 동일한 viewport 크기로 화면을 확인한다.
3. 실제 구현 화면과 Figma screenshot을 비교한다.
4. 다음 순서로 차이를 수정한다.
   - 전체 레이아웃
   - 요소 크기와 위치
   - padding과 gap
   - 폰트와 줄 높이
   - 색상
   - border와 radius
   - shadow와 opacity
   - 이미지와 아이콘
5. 빌드 또는 타입 검사를 실행한다.
6. 오류가 없는지 확인한다.

### 빌드 에러 발생 시

1. 에러 메시지를 분석하여 원인을 파악한다.
2. 타입 에러, import 경로, 누락된 props 순서로 우선 확인한다.
3. 수정 후 다시 빌드하여 에러가 없는지 재확인한다.
4. 동일 에러가 3회 이상 반복되면 사용자에게 보고하고 방향을 확인한다.
5. 에러 수정을 위해 기존 기능을 삭제하거나 API 형식을 변경하지 않는다.

Figma와 비교하지 않은 상태에서는 작업을 완료했다고 판단하지 않는다.

## 7. 작업 완료 보고

작업 완료 시 다음을 보고한다.

- 생성한 파일
- 수정한 파일
- 재사용한 기존 컴포넌트
- 새로 만든 컴포넌트
- 실행한 검사와 결과
- Figma와 완전히 동일하게 구현하지 못한 부분
- 디자이너에게 확인해야 할 부분
